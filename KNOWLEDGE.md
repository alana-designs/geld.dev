# Expense Tracker — Project Knowledge

Living reference for Claude (and future you) across sessions. Update this as decisions get made or things change — don't let it go stale.

## What this is

The app is named **Geld** (renamed from "Expense Tracker" in commit 2f95915; reflected in index.html title, SideRail, mobile header, App.tsx).

A manual-entry-only household budget tracker. Core thesis: bank-linking/auto-import removes the behavioral benefit of *knowing where money went because you typed it in*. No Plaid, no CSV import, no receipt OCR — ever (this is a permanent non-goal, not a v1 gap). Full product thinking lives in `src/docs/manual_budget_app_prd.md`.

## Stack

- **Frontend**: React 18 + TypeScript + Vite, Tailwind CSS, React Router, Framer Motion, Recharts for charts, lucide-react for icons, `xlsx` (SheetJS) for Excel export
- **Backend**: Supabase (Postgres + auth + RLS) — see `supabase/migrations/`
- **Deploy**: Vercel (`vercel.json` present)
- **Migrations are applied by hand** via the Supabase SQL editor / MCP — there is no `supabase db push` history, and `list_migrations` on the project reflects only what's been applied through the MCP tool. `supabase/migrations/` is the authoritative record *by convention*; verify against the live schema rather than trusting a file's presence. All migrations through 0016 are applied (0015 and 0016 on 2026-10-18, through the MCP, file-first). **Note:** 0010–0013 were applied to the live project out-of-band on 2026-08-31 *before* the files existed here, and were transcribed back afterwards — which is exactly the drift this convention is supposed to prevent. Always `list_migrations` before assuming a numbered file is unapplied.
- Scaffolded originally via Magic Patterns, now hand-developed on top

## Data model (see migrations for source of truth)

- `households` → `profiles` (1:1 with `auth.users`) → each profile belongs to one household
- `household_invites`: email-based invite, becomes a profile on signup via `handle_new_user()` trigger
- `categories`: user-owned, parent is one of **Needs / Wants / Savings**, freeform subcategory name, archivable
- `category_goals`: historized (effective_month), so editing a goal doesn't rewrite past goal-vs-actual charts; `goal_for_month()` resolves the goal in effect for any month via rollover
- `transactions`: amount, category, required description, date, owned by one user but readable by the whole household; `recurring boolean` (migration 0003)
- `income_sources` / `income_deductions` / `income_tax_lines`: manual paystub entry (gross pay, pre/post-tax deductions, tax withholdings) → net take-home calculated in app, not stored redundantly beyond `net_override`. `income_sources` has two pay types (migration 0004):
  - **Salaried**: fixed pay frequency; projects a recurring monthly rate. Has `semimonthly_schedule` ('first_fifteenth' | 'fifteenth_last', migration 0010) for which days the paycheck lands (backfilled to `fifteenth_last` for pre-existing rows). Salaried deductions generate server-side payroll auto-savings rows.
  - **Hourly**: one source = one logged paycheck; `paycheck_date` (required) determines which month it counts toward. No frequency field; no payroll auto-savings projections (no fixed schedule to project from). `frequency` on `income_sources` is now nullable.
  - `monthlyNet()` and `totalMonthlyNet()` are month-aware (hourly sources filter to the viewed month; salaried always show). `availableMonths()` accepts `extraMonths` so months with income-only data aren't silently dropped.
- `transactions.source` ('manual' | 'auto', migration 0011): `'auto'` rows are payroll entries generated by `generate_paycheck_entries()`; `'manual'` is everything the user entered.
- `paycheck_entry_skips` (migration 0015): one row per payroll auto-entry its owner deleted by hand, keyed `(income_deduction_id, date)`. The tombstone that stops `generate_paycheck_entries()` re-posting a deleted entry — the transaction row alone can't do it, because the row *is* the idempotency guard. Owner-only RLS (no household read), and the INSERT check pins the deduction to the caller so nobody can suppress a sibling's entry.

**RLS pattern used throughout**: any household member can `select` any other member's rows (shared visibility); only the owning `user_id` can `insert`/`update`/`delete`. `my_household_id()` is a `security definer` helper that avoids RLS recursion through `profiles`.

**Membership is a two-sided handshake** (migration 0008). `household_invites.status` runs `pending → accepted → confirmed`, and only `confirmed` moves anyone: the invitee accepts (`accept_household_invite`, records intent, shares nothing), then the INVITER confirms the address that actually accepted (`confirm_household_member`, which performs the move). That second step is the only thing standing between a mistyped invite and a stranger reading the household — the accepter's display name is theirs to set, so the UI leads with the email. Invites carry `expires_at` (1 hour), set server-side in `send_household_invite()`; direct INSERT on the table is revoked so a client can't write its own expiry. Exits are `leave_household()` and `remove_household_member()`, both of which move the departing member and their rows into a fresh household rather than deleting anything. All of it funnels through `move_member_to_household()`, which is granted to nobody.

**Membership is not a writable column** (migration 0005). `household_id` is the key every read policy resolves through, so it is *not* in the client's UPDATE grant on `profiles` — nor is `id` or `email`. Same for `household_id`/`user_id` on `transactions` and `categories`. The only way to change households is `accept_household_invite(uuid)`, a `security definer` function that requires the invite be addressed to the caller's own confirmed `auth.users.email`. Before this, any signed-in user could rewrite their own `household_id` and read another household's entire ledger.

⚠️ **When adding a column that gates authorization, add it to the revoke list too.** A column-level `revoke` is silently ignored when the role holds a table-level grant — you must `revoke update on <table>` then `grant update (safe, columns)` back. Likewise `revoke execute ... from public` does *not* remove Supabase's direct grants to `anon`/`authenticated` (see 0007).

## Key product decisions (from PRD, section 9)

- Paystub entry is manual-only for v1; OCR/auto-parse is a deferred fast-follow, not started
- Category goals roll over month to month automatically (carry forward until edited)
- Household aggregate view shows combined spending **and** combined take-home income; per-member income stays private to that member's tab except in the rollup total
- USD only, no multi-currency
- Entry flow is amount-first (type $ → pick Needs/Wants/Savings → subcategory → required description) — this is the highest-frequency, must-stay-fast interaction in the app

- **Payroll auto-savings are generated server-side** (as of 2026-08-31). `generate_paycheck_entries(as_of)` (migration 0012) runs daily at 09:00 UTC via `pg_cron` (0013) and inserts *real* `transactions` rows with `source = 'auto'` and `income_deduction_id` set, made idempotent by a unique `(income_deduction_id, date)` index (0011). The client-side `generateAutoEntries()` / `payDatesInMonth()` projection was **deleted** — running both double-counted every entry. `BudgetContext` splits mapped rows into `transactions` (the spend ledger, payroll auto excluded) and `payrollEntries`, exposed as `autoEntriesFor(month)` (view-scoped), `myAutoEntriesFor(month)` (self-scoped, used by Settings) and `allAutoEntries`. Settings and the Dashboard Savings bar still read the same numbers, just from rows instead of a projection.
- **Payroll history restored 2026-10-18** (18 rows, $8,379.96): 6 paydays × 3 deductions at $1,396.66 each — Emergency Fund Contribution $500.00, HSA $146.66, Roth 401k Contribution $750.00 — on 07-15, 07-31, 08-15, 08-31, 09-15, 09-30. Reconstructed, **not** regenerated: `generate_paycheck_entries(<past date>)` reads today's deduction amount, so calling it for a past payday stamps the current rate on history. The amounts came from the user's own 2026-10-07 Excel export, which still held September's six rows verbatim; July/August were inferred from them and corroborated by the $5,586.64 / 4 paydays recorded below, which equals $1,396.66 to the cent. Inserted with `source = 'auto'` and `income_deduction_id` set, so the unique index keeps the cron idempotent over them. **15 October was deliberately left empty** — that payday generated at a stale rate, which is what prompted the delete feature in the first place.
- ⚠️ **Deduction amounts have no history.** `income_deductions` stores one current `amount`, so the generator is only correct when it runs *on* the payday. Every past-date backfill in this file is really a reconstruction, and is only as good as the record it was reconstructed from. Historizing them the way `category_goals` historizes goals is in BACKLOG.md.
- ⚠️ **The generator only ever writes for `as_of`** — there is no backfill, so any month before the job existed has no payroll entries unless `generate_paycheck_entries(<date>)` is called for those dates. It also skips deductions with no `category_id`, where the old client projection fell back to the first unarchived Savings category. July and August 2026 were backfilled by hand on 2026-08-31 by calling it for 2026-07-15, 07-31, 08-15 and 08-31 (12 rows, $5,586.64) — the 08-31 payday needed it because the cron had already run at 09:00 UTC that morning, before 0014 pinned the schedule. Re-running is safe: the unique index makes it a no-op.
- **Deleting one payroll savings entry** (2026-10-18, migration 0015): expand an `Auto · from paycheck` entry in Activity or on the Dashboard and "Delete this one" (tap-to-confirm, same pattern as EntrySheet) removes it. Goes through `delete_paycheck_entry(p_transaction_id)` — SECURITY INVOKER, so the caller's own RLS decides — which writes the `paycheck_entry_skips` row and deletes the transaction in one statement, so a half-done delete can't strand either half. Scoped to that one pay date by design: the deduction keeps its amount and the next payday generates normally. `deleteTransaction()` in BudgetContext picks the RPC vs. a plain delete off the raw row's `source`/`income_deduction_id`, so call sites didn't change. Recurring auto-entries stay undeletable — they're projections with no row behind them.
- **Editing an income source used to wipe its payroll history** — fixed 2026-10-18 (migration 0016). `saveIncomeSource()` handled an edit by deleting every `income_deductions` row for the source and re-inserting them with fresh ids; `transactions.income_deduction_id` was `ON DELETE CASCADE`, so every auto entry those deductions had ever generated went with them, silently. **This is why every payroll entry vanished** — zero `source = 'auto'` rows survived to 2026-10-18. They have since been **restored** (see the restore note above). Two changes closed it:
  - `saveIncomeSource()` now **reconciles deductions by id**: it updates the rows that still exist, inserts the genuinely new ones, and deletes only the ones the user actually removed. A deduction's id is the anchor for every entry it generated and every skip tombstone, so an id must survive an edit. Ids that come back from the DB — not the ones we sent — rebuild local state, so a row deleted in another tab drops out instead of lingering. The sheet mints `d-…`/`pt-…` ids for unsaved rows, so "is this id in `rawDeductions`?" is what separates an update from an insert; a uuid test would be guessing.
  - `transactions.income_deduction_id` is now **`ON DELETE SET NULL`** (0016). Even on a *genuine* delete the posted entries stay in the ledger, orphaned but intact — the money really did leave those paychecks on those dates. The partial unique index from 0011 is `where income_deduction_id is not null`, so nulled rows drop out of it and `generate_paycheck_entries()`'s idempotency is untouched. `paycheck_entry_skips` still cascades on purpose: deduction ids are DB-generated, so an orphaned skip could never match a new deduction.
- ⚠️ **Payroll entries now outlive their income source.** Because of the `SET NULL` above, deleting an income source (which cascades to its deductions) leaves its past payroll entries in the ledger as orphans — `source = 'auto'` with no `income_deduction_id`. That is the intended reading of "a posted entry is a historical fact", but it means deleting a paycheck no longer tidies up after itself. Orphans are still individually deletable: `EntryRow` decides whether to offer the delete from `autoSource === 'income'` rather than from `incomeDeductionId` (which would hide the control on exactly these rows), and `deleteTransaction()` routes them to a plain delete instead of `delete_paycheck_entry()`, which needs a deduction to tombstone. There is no UI that lists orphans or cleans them up in bulk.

## Auth/profile coupling (note)

A `profiles` row and its `auth.users` row must be deleted in that order — deleting the profile alone leaves a working login with no app data, and `handle_new_user()` only fires on INSERT, so it never backfills. That user then hits `.single()` on a missing profile and the app sticks on a blank screen with no recovery. Delete from **Authentication → Users** (which cascades to profiles), never from the Table Editor. Two test accounts hit this on 2026-08-22 and were cleaned up. Migration 0009 adds `ensure_profile()`: the load path in `BudgetContext` uses `maybeSingle()` and calls it when the profile fetch comes back empty, creating a fresh household of one. It's idempotent, and takes a per-user advisory lock so two tabs opening at once can't create two households. It deliberately does not try to restore prior membership — the old rows went with the deleted profile, and rejoining is an invite away.

## Sign-in: Google + magic link (2026-10-18)

Two ways in, one account. `/login` is a real route (`Gate` in `App.tsx`): signed-out visitors are redirected there with the path they were after stashed in `sessionStorage`, and bounced back to it once a session lands. `AuthModal` is now only the signed-in account panel — it no longer handles signing in.

The screen is a port of a Claude Design comp: sign-in card on a canvas column, forest-green stage beside it running a looping fake ledger (`LoginShowcase.tsx` — decorative, `aria-hidden`, still for `prefers-reduced-motion`, and it touches nothing real). Its styles live in `src/pages/Login.css` rather than Tailwind, because the comp leans on layered radial gradients, `mask-image` and keyframes. **Every rule in that file is scoped under `.geld-login`** — the comp's class names (`.card`, `.row`, `.badge`, `.dot`, `.btn`) are generic enough to wreck the rest of the app otherwise. Two deliberate departures from the comp, which was drawn while Google was still only planned: the Google button is live instead of badged "Soon", and it carries Google's own mark rather than a plain letter G.

**Existing magic-link accounts are not disrupted.** Supabase Auth automatically links a new identity to an existing user when the email matches and both sides are verified (Google always returns a verified email; magic-link accounts are confirmed by definition). So an established user signing in with Google for the first time keeps the same `auth.users.id`, and therefore the same `profiles` row, household, and history. No new row is inserted into `auth.users`, so `handle_new_user()` does **not** fire for them.

The one real failure mode: someone whose Google address differs from the email they originally signed up with gets a genuinely separate account and an empty household. Nothing in Supabase can detect that — the login copy should steer people to the address they already use.

Migration 0017 (applied 2026-10-18) adds `signup_display_name()` and rewires `handle_new_user()` to prefer Google's `given_name` (then the first word of `full_name`/`name`) over the email's local part. New accounts only; it cannot touch anyone who already exists. Magic-link signups carry no such metadata, so they still get the email's local part exactly as before.

**Drift caught while writing it, worth remembering:** `handle_new_user()` in `0001_init.sql` still contains the original "join whichever household has a pending invite for this email" branch. That branch was deleted by 0005 and is *not* in the live database. A `create or replace` written from the 0001 file would have silently restored it — reopening the exact capture hole 0005 closed, where anyone who inserted an invite for an address could absorb that person's signup with no accept or confirm step. 0017 is written from `pg_get_functiondef()` on the live function instead, and says so in its header. Read the live definition before replacing any function whose file history spans a security migration.

**Dashboard config this depends on** (not in migrations, set by hand): Google enabled under Authentication → Providers with a Google Cloud OAuth client, and Site URL / Redirect URLs covering `https://geld.dev/**` plus `http://localhost:5173/**` for local work.

## Security posture (audit 2026-08-20)

Fixed in 0005–0007:
- **Cross-household read via writable `household_id`** (critical) — see the RLS note above.
- **Silent household capture on signup** (critical) — `handle_new_user()` used to join a new user to whichever household held a pending invite for their email, with no accept step. Anyone could insert an invite for any address, so a squatted invite (or an inviter's typo landing on a real stranger) handed over the ledger. Signup now always creates a household of one; joining requires `accept_household_invite()`.
- **`household_id` unpinned on UPDATE** for `transactions`/`categories` — INSERT checked it, UPDATE didn't, so a user could push their own rows into another household.
- Anon-reachable `security definer` RPCs; `goal_for_month` mutable `search_path`.

Known and *not* yet fixed:
- **Income is not private within a household.** RLS grants every member full read of `income_sources`/`income_deductions`/`income_tax_lines` — gross pay, every deduction, every tax line. The PRD's "per-member income stays private to that member's tab" is enforced only by which React tab is rendered, not by a policy. Decide whether that's a real promise before building on it.
- **Verify the Supabase redirect allowlist** (Auth → URL Configuration). `sendMagicLink` passes `emailRedirectTo: window.location.origin`; if that list is wildcarded, a cloned app can have a magic-link token delivered to its own domain.
- Table policies from 0001 are still scoped `to public` rather than `to authenticated`; re-scoping them would let `my_household_id()` drop its anon grant too.
- `xlsx@0.18.5` carries CVE-2023-30533 / CVE-2024-22363. Low exploitability (input is the user's own data), but the fixed builds live off-npm.
